🏛️ Engenharia de Software — Código que Sobrevive

SOLID com exemplo real, a pirâmide de testes e as arquiteturas (camadas, hexagonal, DDD) — o que separa código que funciona de código que continua funcionando com o time crescendo.

1. SOLID Sem Cerimônia

LetraPrincípioEm uma frase
SResponsabilidade únicaum motivo para mudar por módulo
OAberto/fechadoestenda por composição, não editando o núcleo
LSubstituição de Liskovsubtipo honra o contrato do tipo
ISegregação de interfacesinterfaces pequenas e específicas
DInversão de dependênciadependa de abstrações, não de implementações

O D na Prática (TypeScript/Go)

interface Notifier {
    Send(to string, msg string) error
}

type OrderService struct {
    notifier Notifier  // abstração!
}

func (s *OrderService) Confirm(order Order) error {
    // ... regra de negócio ...
    return s.notifier.Send(order.Email, "Pedido confirmado")
}

// EmailNotifier, SmsNotifier, FakeNotifier (testes) - o serviço não muda.

A regra de negócio ficou testável sem rede e aberta a novos canais sem edição.

2. Testes — A Pirâmide e o Hábito

E2E (poucos)
Integração (alguns)
Unitários (muitos, milissegundos)
  • Unitários: funções e regras puras
  • Integração: repositório + banco real em container
  • E2E: fluxo crítico de ponta a ponta

Anatomia AAA: Arrange (monta cenário) → Act (executa) → Assert (verifica comportamento)

💡 TDD pragmático: escreva o teste antes quando o design está nebuloso.

3. Arquitetura: Camadas → Hexagonal → DDD

Camadas

Controller → Service → Repository. Suficiente para muita coisa; o pecado é vazar SQL no controller.

Hexagonal (Ports & Adapters)

Domínio

(regras de negócio)

HTTP (adaptador entrada) Postgres (adaptador saída) Fila (adaptador saída)

O domínio no centro, sem saber de HTTP nem de Postgres.

DDD (O Essencial)

  • Entidades: identidade
  • Value Objects: valor imutável
  • Agregados: fronteira de consistência
  • Repositórios: por agregado
  • Linguagem ubíqua: código fala o idioma do negócio

📝 Exercícios — 25 questões

1. Aponte a violação de S: classe UserService que valida, salva no banco, envia e-mail e formata o JSON de resposta.
✅ Correta! Quatro motivos de mudança numa classe; separe validação, persistência, notificação e apresentação.
2. Escreva (pseudocódigo) o teste unitário de OrderService.confirm usando um FakeNotifier.
✅ Correta! Arrange: FakeNotifier gravando chamadas; Act: confirm(order); Assert: fake recebeu (email, msg) e pedido mudou de status.
3. Na hexagonal, onde vivem: regra de desconto, controller HTTP, repositório Postgres, cliente de fila?
✅ Correta! Domínio (centro); adaptador de entrada; adaptador de saída; adaptador de saída.
4. Defina agregado e dê um exemplo do seu domínio de trabalho.
✅ Correta! Fronteira de consistência transacional — ex.: Pedido + Itens (mudam juntos, versão única).
5. Por que "testar detalhes internos" cria testes que quebram em toda refatoração?
✅ Correta! Detalhes mudam sem mudar comportamento; teste acoplado a detalhe pune a melhoria.
6. O que é SOLID?
✅ Correta! Conjunto de 5 princípios de design de software orientado a objetos.
7. O que é Single Responsibility Principle (SRP)?
✅ Correta! Uma classe deve ter apenas um motivo para mudar.
8. O que é Open/Closed Principle (OCP)?
✅ Correta! Código deve ser aberto para extensão, fechado para modificação.
9. O que é Liskov Substitution Principle (LSP)?
✅ Correta! Subtipos devem ser substituíveis por seus tipos base.
10. O que é Interface Segregation Principle (ISP)?
✅ Correta! Interfaces pequenas e específicas, em vez de uma interface grande.
11. O que é Dependency Inversion Principle (DIP)?
✅ Correta! Dependa de abstrações, não de implementações concretas.
12. O que é arquitetura hexagonal?
✅ Correta! Arquitetura onde o domínio está no centro, com adaptadores para entrada (HTTP) e saída (banco, fila).
13. O que é DDD (Domain-Driven Design)?
✅ Correta! Abordagem de design focada no domínio do negócio e linguagem ubíqua.
14. O que é refactoring?
✅ Correta! Processo de melhorar a estrutura interna do código sem alterar seu comportamento externo.
15. O que é teste unitário?
✅ Correta! Teste que verifica a menor unidade de código (função/método) isoladamente.
16. O que é teste de integração?
✅ Correta! Teste que verifica a interação entre múltiplos componentes (ex: código + banco).
17. O que é teste E2E?
✅ Correta! Teste que verifica o fluxo completo do sistema, do início ao fim.
18. O que é TDD (Test-Driven Development)?
✅ Correta! Prática onde os testes são escritos antes do código: Red → Green → Refactor.
19. O que é design pattern?
✅ Correta! Solução reutilizável para problemas comuns em design de software.
20. O que é linguagem ubíqua no DDD?
✅ Correta! Vocabulário comum compartilhado entre desenvolvedores e especialistas de domínio.
21. O que é injeção de dependência?
✅ Correta! Padrão onde as dependências de um objeto são fornecidas externamente em vez de criadas internamente.
22. O que é mock em testes?
✅ Correta! Objeto simulado que substitui uma dependência real para isolar o teste.
23. O que é cobertura de código?
✅ Correta! Medida de quanto código é executado pelos testes.
24. O que é CI/CD?
✅ Correta! Integração Contínua / Entrega Contínua: práticas de automação de build, teste e deploy.
25. O que é boa prática em engenharia de software?
✅ Correta! Prática recomendada que melhora qualidade, manutenibilidade e eficiência do código.
